## ⚙️ SpecCore 拆分原则

SpecCore 核心理念: "Code by Spec, Not by Vibe" — 每个任务必须有对应的 Spec，AI 在 Spec 约束下工作。

### 原子任务定义
一个原子任务 = 一个开发者在指定粒度内可独立完成的、有明确验收标准的最小工作单元。
判定标准（全部满足）:
- 有独立的输入/输出（API 接口 / 页面 / 数据表）
- _shared/ + {端}/TASK.md 能独立写满（REQ.md + TECH.md + 各端子任务）
- execute 时不强依赖其他 Task 的运行时状态
- 有明确的验收标准（AC 可枚举）
- 可独立提 PR、独立 review

### 合并规则（优先合并，减少任务数）
- 同一数据实体的 CRUD → 共享数据模型，合并为 1 个任务
- 页面 + 对应后端接口 < 5 个 → 前后端强耦合，一人做效率最高
- 纯配置/文案/样式微调 → 不构成独立工作单元
- 关联紧密的小功能（如列表页 + 详情页）→ 共享路由和状态
- **复杂度判断**：如果一个需求章节接口 ≤ 3、数据表 ≤ 1、预估工时 < 粒度下限 → 必须合并到最相关的任务，不单独拆
- **宁少勿多**：任务数越少越好，每个任务应该是真正独立的工作单元。如果两个功能共享数据模型或路由，一人就能做完，不要拆

### 拆分规则
- 超出当前粒度接口上限 → 按业务领域拆
- 超出当前粒度数据表上限 → 按数据层拆
- 超出当前粒度工时上限 → 必须再拆
- 低于当前粒度工时下限 → 合并到关联任务
- 跨端功能 → 按端拆（后端 1 个 + 每个前端各 1 个）
- 独立第三方集成（支付/短信/OSS）→ 独立任务

### 🔍 功能聚合度分析（重要 — 拆分前必须执行）

对 REQUIREMENT.md 中的每个功能模块，判断它是「聚合的」还是「单端的」：

**聚合功能**（涉及多个端）：
- 判定标准：功能的「涉及端」列包含 2 个以上端，或功能描述中涉及多端交互
- 拆分策略：**按端拆分**，每个端一个独立 Task
  - 例：「用户登录」涉及 h5 + backend + admin → 拆成 3 个 Task：
    - Task-NNN-h5-login（h5 端登录页面 + 交互）
    - Task-NNN-backend-login（登录接口 + 鉴权 + 数据模型）
    - Task-NNN-admin-login（管理端登录入口）
  -  错误示例：Task-116-approval-scheduler（跨端功能未拆分）
  - ✅ 正确做法：Task-116-approval-backend + Task-117-approval-admin + Task-118-approval-h5
  - 共享契约：`_shared/API_CONTRACT.yaml` 定义跨端接口
  - 每个 Task 的 scope 只包含该端，不要跨端

**单端功能**（只涉及一个端）：
- 直接生成 1 个 Task，scope 只包含该端
- 但仍需检查隐含跨端依赖（如 admin 页面需要 backend 提供新接口）
- 如有隐含依赖，在 dependencies 中标注，或在 scope 中加入对应端

**判断流程**：
1. 读 overview/REQUIREMENT.md 的功能模块清单 → 查看「涉及端」列
2. 读 overview/ANALYSIS.md → 确认跨端关联和数据流向
3. 读 overview/TECH.md → 了解整体架构中的端交互
4. 对每个功能模块判定聚合度，决定拆分策略

### 类型文档拆分规则（bugs/refactors/research）
与 feature 不同，类型文档采用 **1:1 映射**——每个文档直接对应一个任务，不拆分不合并：
- `bugs/xxx.md` → 1 个 bugfix 任务（一个 bug 就是一个任务，不要把多个 bug 合并）
- `refactors/xxx.md` → 1 个 refactor 任务
- `research/xxx.md` → 1 个 research 任务
- `features/xxx.md` → 按功能单元拆分规则处理（可能 1~3 个 feature 任务）
- **sourceFile 必须填写**：类型文档任务的 sourceFile 就是该文档的相对路径（如 `bugs/login-timeout.md`）

### 依赖关系
- 基础模块（认证/数据库/配置）优先拆出，作为第一批任务
- 依赖链深度 ≤ 3
- 同层级无循环依赖

### 总量约束（功能单元基准）
- 核心原则：以需求的功能单元为基准拆分，而非需求文档的章节划分
- 每个功能单元默认 1 个任务，最多 3 个
- 单次迭代总任务数**不得超过 20 个**（超出说明粒度过细，必须合并）
- 每个任务必须有明确的 owner（对应 STAFFING 中的成员）
- 高优先级任务排在前面
- 没有实质性功能内容的章节（如背景、概述、架构、术语等）不能作为拆分依据

>   - refactor → 重构目标范围（如：数据库层、API网关、状态管理）
>   - security → 安全修复范围（如：SQL注入防护、XSS修复、鉴权加固）

> **sourceFile** 必须填写：该任务对应的 020-specs 源文档路径（如 `bugs/login-timeout.md`、`features/user-auth.md`、`refactors/db-pool.md`），用于在 CONTEXT.md 中生成来源追溯
