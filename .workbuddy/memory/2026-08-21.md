## 第八轮（全局分析落盘不符合要求的诊断与修复）

用户反馈：全局深度分析执行后只生成 ANALYSIS.md + outputs/ 临时报告，写到了迭代目录（Iteration-011），而非按规范生成各类文档写入 `.speccore/GLOBAL/`。

诊断：
1. **意图分析确有「多重检查」**：intent-recognition.ts 置信度分级（high≥80/medium≥50/low）、低置信度拒绝、best-second<15 展示候选确认、意图域确认（speccore 操作 vs 普通对话）、ask-engine.ts 147 行专门规则「全局/全量不映射 dashboard，避免与 analyze --scope global 冲突」。
2. **但意图检查只保证「路由对」，不保证「落盘对」**。落盘规范靠 spec-ask SKILL.md（软约束）+ `--prompt` 指引。
3. **根因：SKILL.md 旧流程与 CLI v7.2.0 分层机制不一致**。SKILL.md 全局分析还是「一次生成所有文档写 GLOBAL」旧流程；CLI analyze.ts 1914+ 已改为 Layer 1-4 分层（1代码索引→2架构关联→3业务深入→4全局汇总），每层产出不同文档。AI 收到两个冲突指引导致混乱。

修复：更新 `.agents/skills/spec-ask/SKILL.md` 全局级分析流程为分层机制，明确每层产出 + 写 `.speccore/GLOBAL/`，并强化禁止项（禁止只生成单个文档收尾、禁止写迭代目录、禁止 outputs 临时报告代替落盘）。

关键事实：全局层最终文档集 = overview/(REQUIREMENT/ANALYSIS/DEPS/FUNCTION_MAP/INTERACTION_MAP/API_CONTRACT.yaml) + platforms/{端}/ + requirements/；GLOBAL_SPEC_FILES 定义在 src/core/spec-paths.ts（REQUIREMENT/ANALYSIS/DEPS/FUNCTION_MAP/INTERACTION_MAP/API_CONTRACT）。`--apply` 全局模式写 `.speccore/GLOBAL/`（analyze.ts 823-888），platforms//requirements/ 按原路径，全局技术文档进 overview/。

## 第九轮（`--with-code` 与 `--src` 语义澄清 — 参数非替代关系）

用户复核一次全局深度分析过程，暴露一个反复出现的参数混淆，澄清如下（对照 src/commands/analyze.ts）：

- **`--with-code` 仍是有效参数，不是旧参数**：AnalyzeOptions.withCode（analyze.ts:80）全程活跃，guide 明确推荐 `speccore analyze --scope global --with-code`（analyze.ts:1908 全量重新分析）。布尔开关 =「分析时附读工程源码」。
- **`--src`/`--source` 是独立参数，不是 `--with-code` 的替代**：解析为 options.source（analyze.ts:1547），语义是「代码分析 — 指定源码目录」（如 `--src backend/src h5-mobile/src`，analyze.ts:6 注释）。
- **`--deep <文档名>` ≠ 获取模板**：v7.2.0 单文档深度分析，参数是具体文档名（如 ARCHITECTURE.md，analyze.ts:114）；「深度档位」由 `--depth quick|normal|deep`（analyze.ts:77）控制。两者都跟「获取分析模板」无关。
- **版本号**：当前 package.json 是 7.2.0，不是 6.92.0。

结论：全局深度分析正确命令仍是 `speccore analyze --scope global --with-code`；落盘必须走分层机制写 `.speccore/GLOBAL/` 各文档，不能只落一个 outputs/ 报告 + 架构图（见第八轮）。

## 第十轮（根因定位：cwd 错位导致读错宪法 + 全局层从没建起来）

用户问「会议系统不是用 `SpecCore-examples/meeting-system/.speccore/CONSTITUTION.md` 这个宪法吗」。排查后确认根因链：

1. **两套 .speccore 并存、互相独立**：
   - 当前 workspace = `SpecCore-CLI/ts-cli`（SpecCore CLI 自身源码仓库），它自己的 `.speccore/CONSTITUTION.md` 端列表是 `app/h5/miniapp/admin`，项目信息只有 `ts-cli` 一行（源码路径 `./`）。
   - 真正的会议系统在 `SpecCore-examples/meeting-system`，它的 `.speccore/CONSTITUTION.md` 正确配了四工程：booking-service/room-service/h5-mobile/admin-web（源码路径 `../outputs-project/...`）。
2. **CLI 读哪套宪法取决于 cwd**：`findProjectRoot()`（src/utils/task-utils.ts:14-27）从 `process.cwd()` 向上找 `.speccore/`。所以在 ts-cli 目录跑 `speccore analyze --scope global`，读到的是 ts-cli 的宪法（app/h5/miniapp/admin），落盘会写到 ts-cli 的 `.speccore/GLOBAL/`，根本不是会议系统。
3. **会议系统全局层从没成功建起来**：`meeting-system/.speccore/GLOBAL/` 只有 GLOSSARY.md + INDEX.md + 空 `platforms/`，缺 `overview/`（REQUIREMENT/ANALYSIS/DEPS/FUNCTION_MAP/INTERACTION_MAP/API_CONTRACT）。迭代级 `020-specs/global/` 有 1109 行实质内容（迭代分析成功过），但全局层始终空。
4. **历史落盘 bug 残留**：`020-specs/` 下有 `工程标识`/`错误码`/`1001`/`1002`/`...` 五个空目录——某次落盘把 markdown 表头（"工程标识""错误码"）和错误码数字当成了文件路径。
5. **context.json 不一致**：meeting-system 的 `currentIteration="meeting-upgrade"`，但实际迭代目录名是 `Iteration-011-meeting-upgrade`。

结论：命令/参数/读源码都对，根因是①落盘没走 `--apply` 而是宿主 AI 手写 outputs/报告；②cwd 错位（在 ts-cli 而非 meeting-system 目录跑 CLI）；③会议系统全局层初始化残缺。正确做法：**cd 到 meeting-system 目录**执行 `speccore analyze --scope global --with-code --prompt` 拿模板 → `--apply '{"REQUIREMENT.md":"..."}' --scope global` 写回。
