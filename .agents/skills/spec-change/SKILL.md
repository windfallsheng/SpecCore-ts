# spec-change — 需求变更与新增（专属逻辑）

> **定位**：`/change` 快捷入口的专属预处理层
> **原则**：不影响 `speccore ask` 的意图识别能力

---

## 调用方式

```
/change [参数]
/change --prompt "新增一个通知功能"
/change --prompt "订单模块加个退款接口" -I Iteration-001
```

---

## 执行流程

```
用户输入 /change [参数]
        │
        ▼
┌───────────────────────────────────────┐
│ Step 1: 参数提取                        │
│ 从用户输入提取 iteration/prompt/response │
└───────────────┬───────────────────────┘
                │
        参数缺失？
                │
        是 ──► 输出交互式提示
                │
        否 ──► 继续
                │
                ▼
┌───────────────────────────────────────┐
│ Step 2: 参数补全                        │
│ iteration 缺失 → 读 context.json         │
│ intent 推断 → 新增 or 变更               │
└───────────────┬───────────────────────┘
                │
                ▼
┌───────────────────────────────────────┐
│ Step 3: 前置校验                        │
│ - 当前迭代是否存在？                    │
│ - 已有 Task 列表扫描                    │
│ - 变更类型判断（新增/变更）             │
│ - 附件检测（inbox/ 目录）               │
└───────────────┬───────────────────────┘
                │
                ▼
┌───────────────────────────────────────┐
│ Step 4: 调用 speccore ask               │
└───────────────────────────────────────┘
```

---

## Step 1: 参数提取

| 参数 | 短名 | 长名 | 必填 | 说明 |
|:---|:---|:---|:---|:---|
| iteration | -i | --iteration | 否 | 目标迭代名 |
| prompt | -p | --prompt | 否 | 生成澄清 Prompt（传入用户原话）|
| response | -r | --response | 否 | 应用 AI 澄清结果（JSON）|
| file | -f | --file | 否 | 附件文件路径 |
| task | -t | --task | 否 | 指定受影响的 Task |

## 核心流程（保留）

```
用户自然语言输入（如 "新增一个通知功能" 或 "订单模块加个退款接口"）
        │
        ▼
┌─ 1. 澄清 Prompt ──────────────────────────────────────┐
│  execute_command("speccore change --prompt \"{用户原话}\"")│
│  → CLI 输出澄清 Prompt（含附件 + 已有任务上下文）       │
└───────────────┬────────────────────────────────────────┘
                │
                ▼
┌─ 2. AI 澄清 ──────────────────────────────────────────┐
│  你（AI）根据 Prompt 生成结构化 JSON:                   │
│  {                                                     │
│    "intent": "new" | "change",                         │
│    "structuredDesc": "结构化需求描述",                  │
│    "keyPoints": ["功能要点1", "功能要点2"],             │
│    "acceptanceCriteria": ["验收标准1", "验收标准2"],     │
│    "impactReport": { "directTasks": [...], ... }       │
│  }                                                     │
└───────────────┬────────────────────────────────────────┘
                │
                ▼
┌─ 3. ⚠️ 展示给用户确认（关键！）──────────────────────┐
│  将澄清结果以易读格式展示给用户:                       │
│                                                       │
│  📋 需求澄清结果:                                     │
│  - 意图: 🆕 新增 / 🔄 变更                            │
│  - 结构化描述: ...                                     │
│  - 功能要点: 1. ... 2. ... 3. ...                     │
│  - 验收标准: ☐ ... ☐ ...                              │
│  - 影响范围: Task-001(直接), Task-003(间接)            │
│                                                       │
│  然后问用户: "以上理解是否正确？需要调整什么？"         │
│                                                       │
│  ┌─ 用户说"可以/确认" ─→ 进入步骤 4                   │
│  └─ 用户说"不对/要改" ─→ 根据反馈重新澄清（回步骤 2） │
│                                                       │
│  ⚠️ 这一步不可跳过！必须让用户确认后才写入文件。      │
└───────────────┬────────────────────────────────────────┘
                │ 用户确认
                ▼
┌─ 4. 持久化 ───────────────────────────────────────────┐
│  execute_command("speccore change --response '{JSON}'")│
│  → CLI 解析 JSON → 写入 REQ.md / CHANGE_SUMMARY.md    │
│  → 新增: 创建 Task 目录 + 00-specs/REQ.md             │
│  → 变更: 更新受影响任务的 Spec + 记录变更历史           │
└───────────────┬────────────────────────────────────────┘
                │
                ▼
┌─ 5. 后续引导 ─────────────────────────────────────────┐
│  新增需求 → 引导用户: "接下来可以 analyze 或 split"    │
│  需求变更 → 引导用户: "受影响任务需要 re-execute"      │
└───────────────────────────────────────────────────────┘
```

## 铁律

1. **澄清结果必须展示给用户确认** — 不能 AI 自己决定就写入文件
2. **用户不满意就反复澄清** — 直到用户说"可以"为止
3. **澄清 = 需求分析** — 结果必须持久化到 REQ.md，不是临时判断
4. **不要输出命令文本** — 用 execute_command 执行
