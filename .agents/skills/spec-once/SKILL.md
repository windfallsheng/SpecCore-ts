# spec-once — 单会话端到端执行

## 使用说明（用户仅询问「怎么用/使用说明/使用步骤/能干什么」时，输出本指南，不启动流程）

**它是什么**：SpecCore 的单会话端到端编排技能——把「需求 → 澄清 → 分析 → 拆分任务 → 开发 → 冒烟 → 部署验证」整条链在这一次对话里跑完，全程由 AI 按剧本编排 speccore 命令。

**怎么触发**：直接对 AI 说，例如：
- 「spec once，帮我从 features/ 下的门禁授权同步开始跑」
- 「一次跑完这个文档：/path/to/PRD.docx」
- 「小步快跑：做一个会议室签到功能」（一句话需求也可以）

**三种入口**：
1. **已切好的功能单元**——说单元名或「全部」（建议 ≤3 个，多了建议走流水线）
2. **一个需求文档地址**——.md 直接切分；.docx/.pdf 先转 Markdown 再切分
3. **一句话需求**——AI 先整理成 PRD 级需求文档，再切分

**两种执行模式**：
- **人机交互（默认）**：每个节点停下等你确认（范围 → 分析 → 拆分 → 执行 → 冒烟 → 部署），适合要盯过程的场景
- **全自动**：说「全自动/别停下」即可，节点间不等待；只有三个安全点会停下：范围确认、质量门禁失败、冒烟失败

**六步流程**：① 范围确认 → ② 澄清与分析（生成 020-specs 规格文档）→ ③ 拆分任务（生成 030-tasks 任务）→ ④ 执行开发（生成代码）→ ⑤ 本地冒烟（编译+测试）→ ⑥ 本地部署验证（默认不自动执行，要你说「部署」才做）

**跑完后可继续**：`speccore pr` 提交代码建 PR、`speccore done` 归档收尾（按需，不自动）。

**哪一步不满意可回退重跑**：
- 分析不好 → 重分析该单元（覆盖前自动备份）
- 拆分不合理 → 只重拆指定模块（旧任务自动备份，其它保留）
- 执行不满意 → 重执行单个任务
- 切分不理想 → 重切同名单元三选一（跳过/覆盖/重命名）

**适用边界**：少量单元（≤3）的快速闭环；不适合大范围多单元（走 `speccore run` 流水线）。

## 定位
把「澄清→分析→拆分→执行→冒烟→部署验证」六步装进一次会话，一步到位。
底层全部复用 speccore 现有命令，本 skill 只做编排与交互节点（像 article-to-html 一样
把复杂流程装进一份剧本）。

## 执行模式（入口先识别）

**默认：人机交互模式**——每个节点停下等用户确认（范围 → 澄清 → 分析 → 拆分 → 执行 → 冒烟 → 部署）。

**全自动模式**——用户说「全自动 / 自动跑 / 一路跑完 / 别停下 / --auto」时启用：
- 节点间不等待确认，自动推进：分析完直接 taskify → 拆分完直接 execute → 执行完直接冒烟
- **仍必须停下的三个安全点**：① 范围确认（起点，必须知道范围）② 质量门禁失败/阻塞项 ③ 冒烟失败（最多 2 轮修复循环）
- 部署验证（Step 5）默认不自动执行（涉及环境与账号），只提示命令
- 用户中途说「停下/改为手动」→ 立即切回交互模式，后续节点恢复确认

## 流程（逐步执行，禁止跳步；交互模式每节点停下，全自动模式仅三个安全点停下）

### Step 0 入口识别与范围确认

先识别用户给了什么，按入口执行预处理，再统一做范围确认：

**入口 A：已切分好的功能单元**（用户指定了单元名或说「全部」）
- 无需预处理，直接进入下方「范围确认」
- 用户只给单元名（如「features/ 下的 v3-service-01-门禁授权同步」）时：先 `speccore status` 探测活跃迭代（.speccore/local/context.json 的 currentIteration）；探不到或单元不在该迭代，向用户确认迭代名，不要猜

**入口 B：一个文档地址**（.md / .docx / .pdf，多个文档可批量）
- `.md` → 执行 `speccore unitize -f "<路径>"`（多文档可 `--files "a.md=端1,b.md"`，端名须与 CONSTITUTION.md 一致）
- `.docx/.pdf` → 先执行 `speccore doc2spec -f "<路径>"` 转换为 MD，再对 converted/ 下转换出的 MD 执行 unitize 切分
- 切分完成后汇报单元清单，进入下方「范围确认」

**入口 C：一句话需求**
- 执行 `speccore req-doc "<用户原话>" --prompt --to <迭代>`，按 `[SPECCORE_PROMPT]` 把口语化需求整理为 PRD 级需求文档
- 落盘后再走入口 B（unitize 切分该文档），进入下方「范围确认」

**范围确认（三入口统一汇合点）**
1. 执行 `speccore status` 查看当前迭代、功能单元清单（010-requirements/features/）、020-specs 已有产物
2. 向用户确认本次范围：指定哪几个功能单元，还是全部
3. 边界提醒：单会话建议 ≤3 个单元；全部单元时警告「上下文可能超载，建议分批或改用流水线」，用户坚持再继续
4. 对每个单元检查 020-specs/{单元}/ 是否已有分析产物——有则交互模式问用户「跳过 / 重新分析」；全自动模式默认跳过（用户明确要重分析时走步骤回退重跑协议）
5. 目录/任务命名由 CLI 确定性生成（单元目录 {文档slug}-{序号}-{标题}、Task-{编号}-{slug}、子任务 Task-{父任务}-{端名}），不要自己改

### Step 1 澄清与分析
1. 执行 `speccore analyze --prompt -I <迭代> --with-code`（--with-code 使 Prompt 携带各端工程路径表与源码上下文；指定范围用 `--unit`，直接写切分出的目录名即可——如 `--unit "v3-service-01-门禁授权同步"` 或 `--unit M-01,M-03` 均可（v8.3.250+ 目录名与 M-ID 双匹配）；不要用 --feature——那是确定性局部分析，不出 Prompt）
2. stdout 出现 `[SPECCORE_PROMPT]` → 将 Prompt 内容作为你的工作指令执行（不要改写、不要略过）；多单元时按 Prompt 内的「逐个单元」指示处理，每个单元用 `analyze --unit <id> --apply '<内容>'` 提交
3. 分析中发现需求模糊点 → **向用户提问澄清**，不要自行脑补
4. 分析完成后按 Prompt 中的写入格式执行 `speccore analyze --apply '{json}' -I <迭代>` 落盘
5. 向用户汇报分析产出摘要（单元、文档、关键结论），交互模式**停下等确认**；全自动模式直接进 Step 2

### Step 2 拆分任务
1. 用户确认后执行 `speccore iteration taskify -i <迭代>`
2. 若报告「🔴 阻塞项」（如 ANALYSIS.md 缺失）→ 回到 Step 1 补齐分析产物再重试，不要跳过阻塞
3. 展示拆分出的任务清单（030-tasks/Task-*）与依赖关系
4. 交互模式**停下问用户**：任务拆分是否合理？需要调整吗？；全自动模式直接进 Step 3

### Step 3 执行开发
1. 用户确认后，逐任务执行 `speccore execute --prompt -t <Task>`
2. 拿到 `[SPECCORE_PROMPT]` 后按 Prompt 写代码（写到 CONSTITUTION.md 声明的源码路径，禁止写入迭代目录）
3. 每个任务完成后简短汇报，继续下一个任务
4. 全部完成后输出总结（完成的任务、产出文件、遗留问题）

### Step 4 本地冒烟
1. 执行 `speccore verify --stage dev`（编译 + Lint + 单元测试，代码层冒烟，不依赖浏览器）
2. 若本次范围含**前端任务**（h5/web 等），再执行 `speccore verify --ui --smoke-only`（UI 层冒烟）
   - 冒烟需要本地服务：先问用户「本地服务是否已启动？」，未启动则提示启动命令（或用户提供 --url）后再跑
3. 冒烟通过 → 汇报通过项清单，交互模式**停下等确认**；全自动模式直接进 Step 5 的提示
4. 冒烟失败 → 读取失败报告定位根因 → 修复代码 → 重新执行本步（最多 2 轮修复循环）
   - 2 轮后仍失败：把失败项写入 .issues.md 并向用户报告，不静默跳过、不谎报通过

### Step 5 本地部署验证（默认不自动执行）
1. 冒烟通过后提示用户：「是否执行本地部署验证 `speccore deploy`？」，由用户决定（涉及环境与账号）
2. 用户确认后执行 `speccore deploy`（走 spec-deploy 流程；参数缺失按 `[SPECCORE_NEEDS_INFO]` 交互收集）
3. 部署完成 → 汇报部署产物清单，**停下等确认**
4. 部署失败 → 读取失败报告定位根因 → 修复 → 重试（最多 2 轮），仍失败写 .issues.md 报告，不谎报成功

## 步骤回退重跑协议

用户对某一步产出不满意时，按以下路径回退（上下文不会错位：重分析读 SOURCE.md 原文，重拆读各单元 REQUIREMENT.md，重执行读 00-specs）：

| 场景 | 回退命令 | 说明 |
| :--- | :--- | :--- |
| **分析内容不好** | `analyze --prompt -I <迭代> --unit <单元>` 重新拿 Prompt，再 `analyze --unit <单元> --apply '<新内容>'` 覆盖落盘 | 覆盖写入前自动备份旧文档；只影响该单元，其它单元不动 |
| **拆分不合理** | `speccore iteration taskify -i <迭代> --modules <模块名>` | v8.3.275+：只重拆指定模块的任务（旧任务自动备份为 .backup-*），其它任务保留；不再需要 --force 全量推倒 |
| **执行不满意** | `speccore execute --prompt -t <Task>` 重新执行该任务 | 已 done 的子任务先 `speccore execute --list-pending` 确认状态，必要时用 --skip 排除已完成的 |
| **切分不理想** | `speccore unitize --file <路径> --on-duplicate overwrite`（覆盖重建）或 `rename`（重命名加后缀） | v8.3.275+：同名单元三选一（TTY 交互），非 TTY 用 --on-duplicate 指定 |

重跑后从该步继续向下推进，前序步骤产物无需重做。

### 可选收尾（不自动执行）
- 全部冒烟/部署通过后，提示用户可选操作：`speccore pr`（提交代码 + 创建 PR）、`speccore done`（归档收尾），由用户决定是否继续

## 输出标记处理
- `[SPECCORE_EXEC: <cmd>]` → 立即执行该命令，不要向用户复述命令文本
- `[SPECCORE_PROMPT]` → 将后续 Prompt 内容作为你的工作指令执行
- `[SPECCORE_NEEDS_INFO]` → 用交互式提问向用户收集缺失参数，收齐后重新执行
- `[SPECCORE_CONFIRM_NEEDED]` → 向用户展示确认项，等确认后再继续
- `[SPECCORE_STEP_DONE]` → 告知用户本步完成，下一步请在同一会话继续执行提示中的命令；上下文紧张时才开新会话用 --resume 继续
- `[SPECCORE_CONTINUE: <path>]` → 优先在同一会话继续下一批（按标记中的命令执行）；上下文紧张时开新对话，先读取 <path> 恢复上下文
- `[SPECCORE_INTENT]` / `[SPECCORE_RESULT]` → 原样转达用户
- 其他 `[SPECCORE_*]` 标记 → 参照 speccore-router 的 SKILL.md 处理

## 铁律
- **默认交互模式：每个节点停下等用户确认**（范围 → 澄清 → 分析 → 拆分 → 执行 → 冒烟 → 部署）；全自动模式下仅三个安全点停下（范围确认 / 质量门禁失败 / 冒烟失败）
- 代码写到 CONSTITUTION.md 声明的源码路径，禁止写入迭代目录
- 禁止自己创建目录、写 Spec 文件绕过 CLI——所有 Spec 操作通过 speccore 命令
- 失败时读取 .issues.md 并向用户报告，不要静默跳过；冒烟不通过不得宣布流程完成
- 单会话上下文不够时（prompt 超预算报错），停下建议用户改用流水线分步执行
- 步骤回退重跑一律走「步骤回退重跑协议」中的命令，禁止手改目录或文档绕过 CLI
