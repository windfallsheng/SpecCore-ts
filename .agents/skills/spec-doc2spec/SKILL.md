# SpecCore doc2spec — AI + Pandoc 双路交叉验证

> **核心设计**：AI 语义理解 + Pandoc 机械提取 = 零数据丢失的文档转换。
> Pandoc 负责"搬砖"（格式转换、图片提取），AI 负责"理解"（语义校验、结构修复、数据补全）。
> 
> **Skill 定位**：本 Skill 是"翻译 + 质检 + 修复"的融合体，在 WorkBuddy/CodeBuddy AI 对话中激活。

---

## 1. 触发条件

用户说以下关键词时激活本 Skill：
- "导入需求文档"、"转换 PRD"、"Word 转 Spec"
- "doc2spec"、"导入 {file} 到 {迭代}"
- "帮我分析这个 PRD"、"把需求文档转成 Spec 格式"
- 用户拖入/上传 .docx/.pdf 文件

## 3. 执行步骤（详细版）

### Step 0: 上下文准备
```
1. 读取 .speccore/CONSTITUTION.md — 了解技术栈、端映射、命名规范
2. 读取 .speccore/local/context.json — 了解当前迭代状态
3. 若用户未指定迭代名，询问或自动推断
4. 确认目标路径：Iteration-{name}/010-requirements/{feature}/
```

### Step 1: Path A — AI 语义提取
```
1. 使用 Read 工具直接读取用户上传的 .docx/.pdf 文件
   - .docx: 直接读取（AI 原生支持 docx 解析）
   - .pdf: 直接读取（AI 原生支持 PDF 解析）
   
2. 从原文中提取以下结构化信息：
   a. 文档标题和章节层级
   b. 需求概述（业务背景、目标用户、核心场景）
   c. 功能需求列表（每个功能的描述、前置条件、后置条件）
   d. 非功能需求（性能、安全、兼容性）
   e. API 接口定义（方法、路径、请求/响应参数）
   f. 数据模型/实体定义
   g. 业务规则和约束
   h. UI/UX 描述（页面元素、交互逻辑）
   i. 跨端差异说明（如果文档中有区分 APP/H5/小程序/admin）
   j. 附件和参考引用

3. 将提取结果记录为结构化笔记（JSON/Markdown），命名为 .semantic-extract.json
```

### Step 2: Path B — Pandoc 机械转换
```
1. 检测 pandoc 是否可用
   - 若不可用：提示安装，并告知用户 "AI 单路提取仍可继续，但建议安装 pandoc 获得完整双路验证"

2. 执行 pandoc 转换：
   speccore doc2spec -f "{source_file}" --iter "{iteration_name}" --no-ai

3. pandoc 产出：
   - 010-requirements/{feature}/README.md（或按端分的 README）
   - 010-requirements/assets/extracted/ 下的图片文件
   
4. 读取 pandoc 的产出文件，获取机械转换结果
```

### Step 3: 交叉验证 — AI 双路对比
```
对每一项进行逐条校验：

┌────────────────────┬──────────────────────────────────────────┐
│ 校验维度           │ 校验方法                                  │
├────────────────────┼──────────────────────────────────────────┤
│ 1. 结构完整性      │ AI提取的章节数 vs Pandoc产出章节数        │
│                    │ 缺失章节 → 标记为 ⚠️ LOST，从AI提取补回  │
├────────────────────┼──────────────────────────────────────────┤
│ 2. 标题层级        │ H1/H2/H3 层级是否合理                     │
│                    │ 层级断裂 → 标记为 ⚠️ LEVEL，自动修复       │
├────────────────────┼──────────────────────────────────────────┤
│ 3. 表格完整性      │ API 表格是否完整（列数、行数、表头）       │
│                    │ 表格错位 → 标记为 ⚠️ TABLE，从AI提取重建  │
├────────────────────┼──────────────────────────────────────────┤
│ 4. 图片引用        │ 图片数量是否一致，引用路径是否正确          │
│                    │ 缺失引用 → 标记为 ⚠️ IMAGE                 │
├────────────────────┼──────────────────────────────────────────┤
│ 5. 中文字符        │ 是否存在乱码、编码错误                      │
│                    │ 乱码 → 标记为 ⚠️ ENCODING，用AI提取替换   │
├────────────────────┼──────────────────────────────────────────┤
│ 6. 术语一致性      │ 同一概念是否有多种表达                      │
│                    │ 不一致 → 标记为 ⚠️ TERM，统一为规范术语    │
├────────────────────┼──────────────────────────────────────────┤
│ 7. 数据完整性      │ 关键信息是否丢失（人名、数字、日期）        │
│                    │ 丢失 → 标记为 ⚠️ MISSING，从AI提取补回    │
├────────────────────┼──────────────────────────────────────────┤
│ 8. 格式化代码      │ 代码块、JSON/YAML 是否正确格式化            │
│                    │ 格式错误 → 标记为 ⚠️ FORMAT                │
└────────────────────┴──────────────────────────────────────────┘

输出：VALIDATION.md（验证报告）
```

### Step 4: 智能修复
```
1. 对于每个 ⚠️ 标记，优先使用 AI Path 的提取结果进行修复
2. AI Path 也无法确认的部分 → 标记为 📍 UNCERTAIN，加入人工审核区
3. 修复后的内容覆盖 Pandoc 产出的 REQUIREMENT.md
4. 在文件顶部追加交叉验证报告注释：

<!--
  🔍 交叉验证报告 | {timestamp}
  ✅ 结构完整性: {section_count}/{total} 章节通过
  ✅ 表格完整性: {table_count} 个表格通过
  ⚠️  图片引用: {image_fix_count} 处已修复
  ⚠️  编码修复: {encoding_fix_count} 处已修复
  📍 待人工确认: {uncertain_count} 处
  详情见: VALIDATION.md
-->
```

### Step 5: 生成附加产出
```
1. API_CONTRACT.md — 从 API 表格提取的接口定义
   - 按端分组（app/h5/miniapp/admin）
   - 补充请求/响应示例（从原文推断）
   
2. DATA_MODEL.md — 从需求中提取的数据模型
   - 实体名称、字段、类型、约束
   - 实体间关系
   
3. VALIDATION.md — 完整的交叉验证报告
   - 每一步校验的详细结果
   - 已修复的问题和修复方式
   - 待人工确认的问题清单
   
4. 更新 INDEX.md — 记录转换元数据
```

### Step 6: 输出摘要
```
向用户展示转换结果摘要：
- 输入文件大小、页数
- Pandoc 转换耗时
- AI 语义提取的关键信息量
- 交叉验证发现的问题数
- 修复的问题数
- 待人工确认的问题数
- 输出文件路径
- 下一步建议

格式示例：
📊 文档转换完成 — 双路交叉验证报告
━━━━━━━━━━━━━━━━━━━━━━━━

🛠️ Pandoc: 0.8s, 提取 23 张图片

📤 输出:
   ✅ 010-requirements/room-booking/README.md
   ✅ 010-requirements/room-booking/API_CONTRACT.md
   ✅ 010-requirements/room-booking/DATA_MODEL.md
   ⚠️ 010-requirements/room-booking/VALIDATION.md

```

## 4. 参数处理规则

### 必需参数
| 参数 | 含义 | 获取方式 |
| :--- | :--- | :--- |
| 源文件 | 要转换的 .docx/.pdf 文件 | 用户上传/指定路径 |
| 迭代名 | 目标迭代 | 从 context.json 读取或询问用户 |

### 可选参数
| 参数 | 含义 | 默认值 |
| :--- | :--- | :--- |
| --feature | 需求功能名 | 从文件名推断 |
| --platform | 端名（app/h5/miniapp/admin） | 全部端 |
| --no-cross-validation | 跳过交叉验证 | false（默认启用） |

### 参数追问规则
```
- 迭代名缺失 → "请指定目标迭代（如：Q1/Sprint-3），或告诉我迭代目录名"
- 源文件不存在 → 报告错误，询问正确路径
- 多个需求功能 → "检测到多个功能模块，要为哪个功能创建需求文档？"
- 端模糊 → "该需求涉及哪些端？[app] [h5] [miniapp] [admin] [全部]"
```

---

## 5. 错误恢复策略

| 场景 | 处理方式 |
| :--- | :--- |
| pandoc 未安装 | 切换到 AI 单路模式，提示安装 pandoc |
| pandoc 转换失败 | 报告错误信息，建议替代方案 |
| PDF 无法提取文本 | 建议 OCR 预处理或手动提供文本 |
| 图片提取失败 | 从原始文件手动查找，标记为 📍 |
| 文件过大 (>50MB) | 提示分章节转换，不要一次处理超大文件 |
| 已存在同名文件 | 询问：覆盖/合并/重命名 |
